# Итерация 6: время в блоке дата-центров, живая правка и два honest-пути установки

## Context

Сборка `tg7` работает, но прогон вскрыл три вещи — две мелкие и одну
принципиальную.

**В блоке дата-центров нет относительного времени.** У доступности в шапке
стоит «20 из 20 зондов · 5 мин назад», и по нему сразу видно, свежие цифры или
нет. У связи с дата-центрами только «Проверено: 13:27» — приходится считать в
уме. Заодно из сообщения не видно, как часто вообще идёт это наблюдение.

**Сообщение обновляется реже, чем идёт наблюдение.** Связь с дата-центрами
бот спрашивает раз в минуту, а сообщение перерисовывает не чаще раза в пять
минут: иначе вышло бы 1440 правок в сутки ради двух цифр RTT. Ограничение
разумное, но слишком тупое — оно молчит и тогда, когда изменилось что-то по
существу.

**Главное: поставить сторожа поверх оригинального MTProxyL сейчас нельзя.**
`install-tgbot.sh` зовёт `mtproxyl alertbot install`, а такой подкоманды в
оригинале нет — она живёт только в нашем форке. Скрипт упирается в
«Неизвестная команда», отвечает «обновите MTProxyL», и совет этот бесполезен:
`mtproxyl update` качает файлы **из репозитория автора**, адрес зашит в
`mtproxyl.sh:35` простым присваиванием и переменной окружения не
переопределяется.

Отсюда же вторая половина проблемы. Если поставить форк целиком, первый же
`mtproxyl update` перезапишет `mtproxyl.sh` и все библиотеки из списка нового
скрипта — пункт меню, подкоманда `alertbot` и ключ `TGBOT_VARIANT` исчезнут
(последний вычистит первый же `save_settings`). Сам бот при этом продолжит
работать: служба, конфиг, sudoers и бинарник лежат вне `/opt/mtproxyl`, а три
подкоманды `availability`, на которые выданы права, есть и в оригинале.
Ломается ровно управление, а не наблюдение.

Цель итерации — закрыть обе мелочи и сделать оба пути установки честными, с
понятными инструкциями.

## Решения

| Вопрос | Решение |
|---|---|
| Время в блоке дата-центров | «· N назад» рядом с отметкой, плюс строка о том, как часто идёт наблюдение |
| Частота правок | Потолок 5 минут остаётся для спокойного времени, но существенные изменения правят сообщение сразу |
| Установка поверх оригинала | Самодостаточный установщик: не требует форка скрипта вовсе |
| Установка форка целиком | Источник обновлений помнится файлом `/opt/mtproxyl/.repo`, как сейчас помнится ветка в `.branch` |
| Настройки без панели и меню | Свои подкоманды у бинарника: `mtproxyl-alertbot config show\|set` |
| Новые возможности бота | По решению — ничего не добавляем, функционала достаточно |

## Что меняется

### 1. Блок дата-центров — `mtproxyl-alertbot/internal/tgbot/format.go`

- К строке «Проверено» в `writeUplink` (`format.go:225`) добавляется «· N
  назад» — той же функцией `duration`, что и у доступности (`format.go:158`).
- Рядом строка «Наблюдение: раз в минуту» — как «Автопроверка: … раз в 15 мин»
  у доступности (`writeFooter`, `format.go:677`). Интервал приходит из
  `uplink.DefaultInterval`, а не зашивается в текст: если он изменится,
  сообщение не должно врать.

### 2. Правка при существенных изменениях — `internal/tgbot/bot.go`

Прореживание тихих правок (`quietEditInterval`, `bot.go:37`) остаётся, но
получает исключение. Воркер сравнивает новый вердикт связи с прошлым и
выставляет `d.Force`, если изменилось то, ради чего человек читает сообщение:

- сменился уровень (зелёный/жёлтый/красный);
- изменилось число живых писателей;
- появилась или ушла проблема (`Status.Problems`);
- изменилось число дата-центров без писателей.

RTT и счётчики соединений меняются каждую минуту сами по себе — они в список
не входят, иначе исключение стало бы правилом. Сравнение живёт рядом с
`absorbUplink` (`bot.go`), где уже хранится прошлый вердикт.

### 3. Установка поверх оригинала — новый `install-alertbot.sh`

Полностью самодостаточный POSIX-sh установщик: он не зовёт `mtproxyl alertbot`
и вообще не нуждается в форке скрипта. Всё, что ему нужно от MTProxyL, есть в
оригинале 1.4.8:

- три подкоманды `availability status --json`, `details`, `check --json` —
  на них и выдаются права в `/etc/sudoers.d/mtproxyl-alertbot`;
- `PROXY_API_PORT` читается прямо из `/opt/mtproxyl/settings.conf`;
- `auth_header` — из секции `[server.api]` конфига движка.

Дублируется из `lib/alertbot.sh` немного: создание пользователя, каталог,
скачивание бинарника из релиза с проверкой sha256, sudoers, юнит, `config.json`.
Логирование своё — четыре функции в десяток строк вместо зависимости от
`lib/utils.sh`.

Проверка на входе честная: если `mtproxyl availability status --json` не
отвечает, установщик так и говорит — нужен MTProxyL 1.4.8 или новее, — вместо
нынешнего бесполезного совета обновиться.

Прежний `install-tgbot.sh` остаётся тонким переходником на новый: люди уже
разослали ссылку на него.

### 4. Свои подкоманды у бинарника — `mtproxyl-alertbot`

Без панели и без меню форка настройки править нечем, поэтому бот получает свои:

```
mtproxyl-alertbot config show                       # всё, кроме токена
mtproxyl-alertbot config set alert_threshold 60
mtproxyl-alertbot config set connect_fail_threshold 20
mtproxyl-alertbot config set timezone Asia/Tashkent  # пусто — определять самому
mtproxyl-alertbot config set chat_id -1001234567890
```

Пишут они тот же `config.json` через существующий `config.Store` (атомарная
запись уже есть) и перезапускают службу через `systemctl`, если она есть. Токен
`config show` не печатает — только признак, что он задан.

### 5. Источник обновлений — `/opt/mtproxyl/.repo`

В форке `mtproxyl.sh` начинает читать адрес репозитория из
`${INSTALL_DIR}/.repo` — ровно так же, как сейчас читает ветку из `.branch`
(`mtproxyl.sh:35-44`). Установщик форка записывает туда себя. Тогда
`mtproxyl update` тянет файлы форка, и ни пункт меню, ни подкоманда, ни
`TGBOT_VARIANT` не пропадают.

Заодно чинится ещё одна дыра: в списке библиотек `install.sh:119` нашего форка
нет ни `alertbot`, ни `tui_alertbot` — то есть свежая установка форка их
сегодня не притаскивает вовсе. Добавляются оба.

И `self_update` (`lib/utils.sh:576`), который после обновления дёргает
`tgbot_update_sources`, начинает так же обновлять бинарник сторожа, если тот
установлен.

### 6. Инструкции — README

Два пути, честно про цену каждого:

**Путь 1 — поверх оригинального MTProxyL (рекомендуемый).** Одна команда,
обновления автора ничего не ломают: сторож живёт своей службой и от файлов
MTProxyL не зависит. Управление — командами `mtproxyl-alertbot config …`.
Пункта меню и раздела в панели не будет.

**Путь 2 — форк целиком.** Пункт меню, выбор бота и раздел в панели.
Обновления приходят из форка (`.repo`), то есть ровно тогда, когда апстрим
слит в форк. Как вернуться на оригинал: удалить `.repo` и выполнить
`mtproxyl update`.

Отдельным абзацем — что делать, если автор поменяет что-то кардинально:
сторож переживает это по построению, пока цела команда
`mtproxyl availability status --json`; если она изменится, бот скажет об этом
в сообщении и в журнале, а лечится обновлением сторожа.

## Проверка

Как в CI: `gofmt -l`, `go vet`, `golangci-lint run`, `go test -race ./...` в
обоих модулях, `npm run build`, `bash -n`/`sh -n` по всем правленым скриптам.

Тестами закрываются: относительное время и строка интервала в блоке связи;
правка сообщения при смене числа живых писателей и молчание при изменении
одних лишь RTT; разбор и запись настроек подкомандой `config set`.

На ноде:
1. На **оригинальном** MTProxyL 1.4.8 выполнить `install-alertbot.sh` — бот
   поднимается, в чате появляется сообщение с обоими блоками.
2. Там же `mtproxyl update` — служба продолжает работать, сообщение живое.
3. `mtproxyl-alertbot config set alert_threshold 70` — значение видно в
   сообщении после перезапуска службы.
4. На форке: `mtproxyl update` не уносит пункт меню и подкоманду `alertbot`.
5. Уронить связь с дата-центрами — сообщение правится сразу, а не через пять
   минут; в спокойное время правки идут не чаще раза в пять минут.
