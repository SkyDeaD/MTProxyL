# Итерация 5: обновление под MTProxyL 1.4.8 и алерт-бот отдельной службой

## Context

Автор апстрима выпустил v1.4.8 / панель 1.0.7 и переделал ровно то место, на
котором стоял наш бот.

**Проверка доступности уехала из панели в скрипт.** Пакет
`mtproxyl-panel/internal/globalping` удалён целиком — вместо него
`lib/availability.sh` (789 строк), состояние в `/opt/mtproxyl/availability`,
расписание держит таймер `mtproxyl-availability.timer`. Панель стала
stateless-прокси: каждая ручка синхронно зовёт `mtproxyl availability …` и
отдаёт то, что скрипт уже измерил. **Подписки на новый вердикт внутри Go
больше нет** — ни `Checker`, ни `SetOnResult`; узнать о новом вердикте можно
только опросом. Наш бот держался ровно на этой подписке и на десяти типах из
удалённого пакета.

**У автора появился свой бот** — `/opt/mtproxyl-tgbot`, python в venv,
служба `mtproxyl-tgbot.service`, отдельный пользователь без прав, доступ к CLI
через поимённый sudoers. Это бот-администратор: управление прокси, пользователи,
ссылки с QR, трафик, бэкапы. Уведомления у него есть, но узкие: доступность
упала/вернулась, прокси лёг/поднялся, кончилась квота у пользователя, итог
автобэкапа. **Мониторинга связи с дата-центрами Telegram у него нет** — а это
ровно та половина картины, ради которой наш бот и делался: фильтрация чаще
режет выход, а не вход, и тогда зонды показывают 95% при неработающих клиентах.

Итог: два бота не конкуренты, а разные инструменты. Цель итерации — обновить
форк под новую версию, вынести наш бот в самостоятельную службу по образцу
бота автора и дать человеку выбор, какой из двух включён, — и в меню скрипта,
и в панели.

Плюс отдельная поломка с боевого сервера: бот прислал новое сообщение вместо
правки прежнего — разбор ниже.

## Решения

| Вопрос | Решение |
|---|---|
| Где живёт наш бот | Отдельная служба `mtproxyl-alertbot`, как у автора. Работает без панели |
| Язык | Остаётся Go: ~4000 строк рабочего кода и 3500 тестов, все зависимости — stdlib |
| Источник вердикта | `mtproxyl availability status --json` по таймеру; проверка по кнопке — `availability check --json` |
| Связь с дата-центрами | Как и была: напрямую в API движка на `127.0.0.1:$PROXY_API_PORT` |
| Одновременная работа | Строго один бот: включение одного останавливает другой |
| Выбор варианта | Ключ `TGBOT_VARIANT` в `settings.conf` — единый источник правды для CLI, TUI и панели |
| PR в апстрим | Пока не трогаем: сначала обкатка на ноде |

## Что меняется

### 1. Обновление форка под 1.4.8

Слить `upstream/dev` в нашу ветку. Конфликты ожидаются только в тех чужих
файлах, которые мы правили, и все правки мелкие: `internal/server/server.go`
(+12), `internal/server/availability.go` (+6), `frontend/src/lib/api.ts` (+65),
`AvailabilityPage.tsx` (+304), `Dockerfile`, `docker-compose.yml`, README.
Крючок в `internal/globalping/checker.go` исчезает вместе с пакетом — он больше
не нужен.

После слияния из панели **уезжают** `internal/tgbot`, `internal/uplink`,
`internal/server/telegram.go` и наш блок на странице «Доступность». Панель
перестаёт содержать бота вовсе — ровно как у автора.

### 2. Новый модуль `mtproxyl-alertbot/`

Отдельный Go-модуль рядом с `mtproxyl-tgbot/` (python) и `mtproxyl-panel/`.
Внешних зависимостей нет — только stdlib, поэтому свой `go.mod` ничего не тянет.

```
mtproxyl-alertbot/
  go.mod
  main.go              — чтение config.json, запуск наблюдателей, graceful stop
  internal/tgbot/      — переезжает как есть (bot, format, client, incidents, …)
  internal/uplink/     — переезжает без изменений
  internal/mtproxyl/   — НОВОЕ: вердикт доступности из CLI
```

`internal/mtproxyl` — тонкий слой вместо удалённого `globalping`:

- `Client{script string, sudo bool}` — запуск `mtproxyl availability …`, разбор
  первой строки JSON. Повторяет приём апстрима (`mtproxylctl.firstJSONLine`).
- Типы под фактический JSON скрипта: `Verdict{Probes []Probe, TotalProbes,
  SuccessProbes int, Percentage float64, Level string, Target, CheckedAt,
  Error, MeasurementID}`, `Probe{City, Country, Network, ASN, Status,
  TLSSuccess, Error}`, `Quota{Budget, Spent, Remaining, ResetInSeconds,
  HasToken}`, `State{Enabled, AutoCheck, TimerActive, Interval, Probes,
  Threshold, NextRun, Quota, Target, Result, Message}`.
- `Poller` — опрос `availability status --json` раз в минуту с определением
  «вердикт новый» по `checked_at`. Это замена подписки: события внутри Go
  больше нет, а держать в чате свежие цифры надо.

`internal/tgbot` правится точечно: `globalping.CheckResult` → `mtproxyl.Verdict`
и так далее по списку из десяти символов; `Deps.RunCheckNow` зовёт CLI;
`hostinfo.go` теряет `globalping.PublicIP` — адрес сервера берётся из
`target.host` вердикта, A-запись резолвится как и раньше своим `net.Resolver`.

### 3. Установка — `lib/alertbot.sh`

По образцу `lib/tgbot.sh`, с теми же приёмами и именами:

- `/opt/mtproxyl-alertbot`, пользователь `mtproxyl-alertbot` (без входа),
  `config.json` с правами 600, служба `mtproxyl-alertbot.service`,
  `/etc/sudoers.d/mtproxyl-alertbot`.
- sudoers — только чтение и проверка: `availability status --json`,
  `availability details`, `availability check --json`. Управлять прокси
  алерт-бот не умеет и права на это не просит.
- Доставка кода отличается от питоновской: у нас бинарник, поэтому качаем
  `mtproxyl-alertbot-<arch>-linux-<libc>.tar.gz` из релиза и **сверяем sha256** —
  готовая механика лежит в `mtproxyl-panel/install.sh:738-808`, повторяем её.
- Подкоманды `mtproxyl alertbot install|setup|uninstall|set|update|start|stop|
  restart|logs|status` — тот же набор и те же флаги, что у `tgbot`, чтобы
  человек не переучивался.
- Адрес и заголовок авторизации API движка установщик добывает так же, как
  установщик панели (`mtproxyl-panel/install.sh:660-680`): порт из
  `mode --json`, `auth_header` — из конфига движка.

### 4. Выбор бота

Ключ `TGBOT_VARIANT` в `settings.conf` (`none|admin|alert`) — один источник
правды; `lib/settings.sh` пополняется им как обычной настройкой.

- CLI: `mtproxyl tgbot install` и `mtproxyl alertbot install` выставляют ключ
  сами и останавливают чужую службу, если та работает. Молча ничего не сносим:
  установка спрашивает подтверждение, а с `MTPROXYL_ASSUME_YES` (режим панели)
  считает согласием.
- TUI: пункт «Телеграм бот» в главном меню остаётся один. Если не установлен
  ни один — экран выбора: «Бот-администратор» / «Бот-сторож» с описанием в две
  строки, чем они отличаются. Если установлен — прежнее меню варианта плюс
  пункт «Сменить бота».
- Панель: на существующей странице «Телеграм-бот» сверху переключатель
  вариантов, ниже — форма выбранного. Для алерт-бота — токен, ID админа, порог
  доступности, порог отказов, часовой пояс.

### 5. Панель: `internal/mtproxylctl/alertbot.go` + ручки

Зеркало `tgbot.go`: `AlertbotStatus/Logs/Install/Service/Uninstall/Set`, тот же
`Client.run`, тот же `ErrTgbotUnsupported`-подобный признак старого скрипта.
Ручки `/api/alertbot/*` повторяют `/api/tgbot/*` и живут рядом в
`internal/server/mtproxyl.go`. Установка — через тот же `runner` долгих
операций, что и у бота автора.

### 6. Сборка и релиз

`.github/workflows/mtproxyl-panel-release.yml` собирает второй бинарник теми же
матрицами (amd64/arm64 × gnu/musl) и кладёт в тот же релиз. Тег общий.

### 7. Переезд тех, кто уже поставил наш бот overlay-скриптом

`install-tgbot.sh` (ветка `tg-testing`) заменяется установщиком новой схемы. Он
переносит `/var/lib/mtproxyl-panel/telegram-bot.json` в
`/opt/mtproxyl-alertbot/config.json` — вместе с `status_message_id`. Без этого
прежнее живое сообщение осталось бы в чате навсегда: нового id у бота нет, а
старое он уже не тронет.

## Поломка: новое сообщение вместо правки

С боевого сервера пришли три сообщения подряд. Первые два объяснимы — это
события со звуком (потеря связи с дата-центрами, затем восстановление плюс
сорвавшаяся проверка Globalping). Третье — обычный статус без единой шапки, и
вот его быть не должно.

Косвенные признаки из самих сообщений: у первого «Проверено: 04:27:13» и квота
420, у третьего — «Проверено: 09:27:13» и та же квота 420. Минуты и секунды
совпадают, разница ровно пять часов — это один и тот же вердикт, отрисованный
в двух разных зонах, причём подпись у обоих одна: «Asia/Tashkent, UTC+05».
То есть между отрисовками сменился часовой пояс, а не время проверки.

**Рассинхрон зоны — доказан.** `localZone()` (`timezone.go:58`) перечитывает
зону не чаще раза в `tzRecheck = 5 минут`, а один рендер зовёт её шестью
независимыми вызовами (`format.go:144` для «Проверено», `format.go:153` для
подписи, плюс `stampShort`, «заглушены до»). Если TTL истекает между двумя
вызовами — или настройки сохраняют из панели, что сбрасывает кэш через
`SetTimezone` (`telegram.go:374`), — часть времени печатается в прежней зоне,
а подпись уже в новой. Сочетание «04:27:13» с подписью «Asia/Tashkent, UTC+05»
при одном значении зоны невозможно: смещение в подписи берётся у того же
объекта зоны. Лечение: зона снимается **один раз на рендер**, кладётся в
`View`, а `stamp`, `stampShort` и `zoneNote` берут её оттуда.

**Лишнее сообщение — три пути, все закрываем.**

1. *Порядок другой, чем кажется.* «N мин назад» считается по монотонным часам
   и от зоны не зависит: у третьего сообщения «5 мин назад», у первого — «13».
   Значит третье отправлено раньше, и настоящий вопрос не «почему пришло
   новое», а «почему прежнее осталось в чате, когда тревога отправила новое».
   Квота меткой времени служить не может — это скользящее часовое окно, и 420
   при проверке раз в 15 минут держится постоянно.
2. *Смена адреса доставки.* `applyConfig` при смене `AdminID` пересоздаёт
   клиента и снимает команды у прежнего владельца (`bot.go:261`), но
   сохранённый `MessageID` остаётся, а он принадлежит **другому чату**. Правка
   уходит в новый чат со старым id, Telegram отвечает «сообщение не найдено»,
   бот шлёт новое — а прежнее висит в старом чате навсегда, потому что убрать
   его больше некому. Лечение: при смене адреса убирать сообщение в старом
   чате там же, где снимаются команды, и обнулять id.
3. *Истёкшая пауза при живой аварии.* `bot.go:517-524` ставит `d.Loud = true`,
   когда пауза кончилась и авария всё ещё идёт, но шапку при этом не добавляет.
   Приходит новое сообщение со звуком и без единого слова о том, почему оно
   пришло. Лечение: своя шапка «🔔 Пауза кончилась, авария продолжается».

Плюс общее: причина переотправки пишется в журнал. В этот раз её пришлось
восстанавливать по косвенным признакам из текста сообщений, и это само по себе
недоработка.

**Каналы и группы поддерживаем явно.** Адресом доставки может быть личка,
группа или канал. В канале нет ни команд, ни клавиатуры — бот их там не
предлагает и не регистрирует; удаление своих сообщений требует прав
администратора, поэтому при запуске бот проверяет права и честно пишет в
панель, если убирать прежние сообщения не сможет. Поле в панели переименуется
из «ID админа» в «ID чата» с подсказкой про все три случая.

## Порядок работ

1. Слить `upstream/dev`, снять зависимость от `internal/globalping`, добиться
   зелёной сборки без бота (панель = чистый апстрим плюс наши мелочи).
2. Поднять модуль `mtproxyl-alertbot`, перенести `tgbot` и `uplink`, написать
   `internal/mtproxyl` и `main.go`. Тесты переезжают вместе с кодом.
3. Починить поломку с новым сообщением, закрыть тестом.
4. `lib/alertbot.sh` + `TGBOT_VARIANT` + TUI.
5. Панель: `mtproxylctl/alertbot.go`, ручки, страница.
6. Сборка в релизе, новый установщик, обкатка на ноде.

Этапы 1–3 самодостаточны: после них бот уже работает на новой версии, просто
ставится вручную. Этапы 4–6 добавляют выбор и удобство.

## Проверка

Как в CI: `gofmt -l`, `go vet`, `golangci-lint run`, `go test -race ./...`,
`go build` и кросс-сборки linux amd64/arm64 — теперь для двух модулей; плюс
`npm run build`. Скрипты — `bash -n` и `shellcheck`, как в апстримном CI.

На ноде:
1. Обновить MTProxyL до 1.4.8 и панель до 1.0.7 — убедиться, что доступность
   считает таймер, а страница панели работает как раньше.
2. Поставить алерт-бот из меню: выбор варианта, токен, ID; служба поднялась,
   в чате одно живое сообщение с обоими блоками.
3. Остановить движок — приходит тревога о связи с дата-центрами; поднять —
   восстановление. Убедиться, что сообщение правится, а не плодится.
4. Переключиться на бота-администратора: алерт-бот остановлен, служба чужая
   поднялась, в панели переключатель показывает актуальное.
5. Перезапустить панель и сервер целиком — бот продолжает править то же
   сообщение.
6. Сменить часовой пояс на сервере — время в сообщении меняется целиком, а не
   наполовину, и нового сообщения не приходит.
7. Сменить адрес доставки (личка → канал) — прежнее сообщение убирается из
   старого чата, новое появляется в новом; в канале команд и клавиатуры бот не
   предлагает.

Тестами закрываются: снимок зоны на рендер (метка и подпись всегда из одной
зоны, даже если TTL истёк посреди отрисовки), уборка сообщения при смене
адреса, шапка про истёкшую паузу.
